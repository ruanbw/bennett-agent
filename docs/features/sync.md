会话数据由浏览器持有（IndexedDB / Dexie），服务端只做镜像与排序依据。同步引擎是前端的一个模块级单例，登录后启动、登出停止；它把本机变更推上去、把服务端变更拉下来，两端最终一致。

**注意**：本地优先指的是「已同步过的内容断网不丢」，不是「可以离线进应用」。启动时要调 `/api/auth/me` 确认登录态，断网会停在登录页（当前没有 Service Worker）。

## 角色分工

| | 本机（IndexedDB） | 服务端（PostgreSQL） |
|---|---|---|
| 谁生成 id | 客户端生成（`sess_` / `msg_` 前缀 + uuid） | 原样存为主键 |
| 谁决定顺序 | 不用本地顺序 | `seq`：服务端赋的会话内顺序 |
| 谁决定新旧 | `client_rev`：本地每次修改 +1 | 按 `client_rev` 比较 |
| 谁是权威 | 不是 | 是（内容与顺序都是服务端说了算） |

客户端的 `created_at` / `updated_at` 只用于展示排序，**不能作为同步判据**——两台设备的时钟本来就不一致。

## 写路径：push（行级幂等 upsert）

`POST /api/sync/push` 一次提交会话行与消息行。服务端逐行判定，整批不会因为某一行坏掉而失败。

写入走 PostgreSQL 的 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING`，条件是 `(user_id = 当前用户) AND (client_rev <= 本次修订号)`。语义：

| 情况 | 结果 |
|---|---|
| 行不存在 | 插入 |
| 服务端 `client_rev` 更小 | 更新（覆盖） |
| 服务端 `client_rev` 更大 | 拒绝 `stale` |
| 服务端 `client_rev` 相同、内容完全一致 | 视为纯重放：只记账，不写库、不推进版本 |
| 服务端 `client_rev` 相同、内容不同 | 按内容应用并记一条 WARNING（客户端漏了 +1 的情况） |

纯重放不写库也不推进版本号，因此不会唤醒该用户的其它设备——否则每次重试都会把所有设备的 pull 叫醒一次再推一遍同样的行。

同一个 id 在一批里出现多次时，取 `client_rev` 最大的那条（重试拼接的批次会这样）。

### 幂等的两个前提

1. **id 由客户端生成**。服务端发主键会让「重试」变成多一行。
2. **修订号单调递增**。服务端靠 `client_rev` 判断新旧；客户端漏了 +1 会让「同修订号不同内容」这种异常状态出现。

### 拒绝原因与客户端动作

| `reason` | 含义 | 客户端该做什么 |
|---|---|---|
| `not_owned` | 这个 id 属于另一个用户 | 丢弃，不再重试 |
| `stale` | 服务端已有更新的 `client_rev` | 丢弃，等下一轮 pull 用服务端版本覆盖；面板单独计数提示「本机修改被覆盖」 |
| `too_large` | payload 序列化后超过 `SYNC_PAYLOAD_MAX_BYTES`（默认 256 KB） | 停止重试，标 error；用户要自己删掉或导出那条内容 |
| `conversation_missing` | 会话不存在（不在本批，也不是自己名下的行） | 会话重新标 pending、消息留 pending，下一批先推会话 |
| `conversation_deleted` | 会话已被删除（墓碑已存在） | 丢弃，不再重试 |
| `quota_exceeded` | 触到单用户会话数或单会话消息数上限 | 标 error，等用户清理旧内容后手动「重新上传」 |

拒绝是**逐行**的：同批其它行照常接受。前端把「永远不会成功」的原因（`stale` / `not_owned` / `conversation_deleted`）直接标成 synced，把「可能成功」的原因（`conversation_missing`）留在队列里重试，把「数据本身放不进去」的原因（`too_large` / `quota_exceeded`）标成 error 并给用户一个显式入口。

### 批量上限

单次 push 的行数上限是 `SYNC_PUSH_MAX_ROWS`（默认 200，会话 + 消息合计）。超了整批返回 400（`code=too_many_rows`），客户端按这个上限分批。客户端一次取 150 行，给服务端留余量。

批次组装还有一条约束：**会话必须先于它的消息到达服务端**（服务端按 id 校验会话归属）。会话数超出一批时，引用这些会话的消息不能塞进同一批——那只会换回一堆 `conversation_missing`。

## 发号与空洞

`seq`（会话内消息顺序）与 `version`（拉取游标用的版本号）都由服务端赋值，客户端不能自己填。

- **会话内顺序**：`conversation.seq_counter` 自增，与消息插入同事务。回滚时序号一起回滚。
- **同步版本号**：每个用户一行 `sync_counter`，用 `INSERT ... ON CONFLICT DO UPDATE ... RETURNING version` 一条语句发号，行锁保证并发 push 不会拿到同一个号。

写入与发号**必须同事务**。分开就会出现「版本前进、行还没写」的空洞：客户端拉到的游标已经越过那条还没写的行，之后永远不会拉到它，数据静默丢失。

时间戳不能替代版本号：毫秒级时间戳在高频写入下会撞，同一毫秒的两行无法区分先后。

## 读路径：pull（不透明游标）

`GET /api/sync/pull?cursor=...&limit=...&timeout=...`

游标是不透明字符串（`v1:<version>`），客户端不许解析，服务端可以随时换格式——换编码时旧游标会被识别为「不认识」并触发 410。

拉的是两路数据：会话行与消息行，各自有独立的行数上限（`SYNC_PULL_MAX_ROWS`，默认 500）。响应还受累计字节上限约束（`SYNC_PULL_MAX_BYTES`，默认 8 MB）：500 行 × 256 KB 最坏是 128 MB，一次就能把序列化与浏览器主线程一起拖死。

### 游标只在两路都拉完时才前进

这是最容易写错的一处。假设会话路被截断、消息路没被截断：

- 游标若取会话路的最后一行版本号 → 消息路里版本号更小的那些行会被永久跳过。
- 游标若取消息路的最后一行版本号 → 同理跳过会话路的行。

所以规则是：**只有一路被截断时取那一路的最后一行版本号；两路都被截断时取较小值**；两路都没截断时取服务端当前 head。多返回的行客户端会重复收到一次，无害——这是幂等的前提。

### 长轮询

无变更时 pull 会挂起等待（`SYNC_LONG_POLL_SECONDS`，默认 25 秒）。等待方先订阅再查版本号：反过来的话，落在「查完」与「开始等」之间的写入会丢掉唤醒，只能白等到超时。

有三种情况直接返回、不挂起：

- 首次同步（不带游标）——客户端要的是全量；
- `has_more=true`——还有下一页要拉；
- 本次已经拉到数据。

唤醒信号当前是进程内实现（每用户一个 `asyncio.Event`）。**多 worker 部署时 A 进程的写入唤不醒 B 进程的等待方**：它不报错也不告警，只会静默等到长轮询超时。要支持多 worker 必须换成 Redis pub/sub，且订阅要在查版本号之前完成。

## 错误分类

| 状态码 | `detail` 里的 code | 含义 | 客户端动作 |
|---|---|---|---|
| 400 | `invalid_cursor` | 游标格式不认识 | 丢弃游标，全量重拉 |
| 410 | `resync_required` | 游标超出服务端当前版本（服务端回滚或换过库） | 丢弃游标，全量重拉 |
| 400 | `too_many_rows` | 单次 push 行数超限 | 按 `SYNC_PUSH_MAX_ROWS` 分批 |
| 429 | — | 同步限流 | 按 `Retry-After` 退避 |

`400 invalid_cursor` 与 `410 resync_required` 对客户端的动作是同一件事：丢掉游标重拉。区别只是服务端能否解释原因。

### 游标反复失效的守卫

客户端对连续失效计数：第一次按原逻辑处理（丢游标 + 把本机数据全部标脏让下一轮 push 补回去），之后的重拉不再重复标脏（标脏会把整库重新推一遍，是风暴的主要放大器），超过 3 次就停下来报错，交给用户点「立即同步」。

不设这个守卫时，「拉 → 410 → 全量拉 → 推 → 拉 → 410」的循环能在一秒内打出几十个请求，最后把自己的账号打成 429。

## 冲突模型

同步是**最后写入者胜出**，但用修订号而不是时间戳判新旧：

- 同一行，两端都改：谁的 `client_rev` 大谁赢。`client_rev` 相等但内容不同时按内容应用并留日志。
- 服务端有的修订号更小 → 覆盖服务端行（正常的跨设备同步）。
- 服务端有的修订号更大 → 拒绝 `stale`，客户端放弃本机那次修改，等 pull 覆盖回来。面板单独计数提示，不静默丢弃。
- **删除是单向的**：墓碑不能被「未删除」的行复活。删除会话会级联删掉它的消息行。
- **新墓碑不落库**：服务端没有这条会话时，`deleted=true` 的行不入库——没有设备同步过它，墓碑无处传播，而允许为任意新 id 写墓碑等于让别人预占会话 id。

本机还有没推上去的内容时（`syncState` 为 pending 或 error），拉到的东西**不覆盖**本地：此时服务端那份是旧的。

## 客户端的调度

- 表级 hook 只负责**打标记**（`syncState = pending`），推送由明确时机触发：一轮生成结束、标签页隐藏、恢复在线、启动、以及用户改动会话（重命名 / 置顶 / 删除）。不是「每次写库都推一次」——流式生成期间每 800ms 写一次助手消息，按写入触发会把中间态反复上传。
- 拉下来的行必须走内部的同步写入路径，否则会被表级 hook 标成 pending 又推回去，形成拉/推无限循环。
- 长轮询超时**不算失败**：单次超时静默重试，连续 3 次才上报。浏览器冻结标签页会让定时器停走，恢复时立刻到期，把它当失败会误报「同步没保存」。
- 断网时停止发请求，等 `online` 事件重新排队；面板把断网显示成「会自动恢复」而不是「同步失败」。
- 登出前有一次最后推送（2 秒预算），返回仍未推上去的行数，界面据此提示「这些内容会丢」。
