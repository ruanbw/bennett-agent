# 参考

这一组是**查阅型**文档，不是阅读型。前面三组回答「怎么用、为什么这样设计」，这一组只回答「具体叫什么、默认多少、报错是什么」。

三页都按同一个原则写：每一条都能指回源码位置。改动代码之后，直接按标注回去核对，不用通读全文。

## 三份清单

| 清单 | 回答什么问题 | 什么时候查 |
|---|---|---|
| [HTTP 端点目录](api.md) | 32 个端点的路径、方法、鉴权、限流桶、请求与响应模型字段 | 接前端、写脚本、对接口 |
| [配置项参考](config.md) | `Settings` 89 个字段的变量名、类型、默认值、启动期校验 | 部署、调参、排查「改了不生效」 |
| [错误码与失败模式](errors.md) | 每条错误的触发条件、状态码、错误标识、该改什么 | 排障、写客户端错误处理 |

## 和另外三组的分工

同一个话题往往有两页，分工是固定的，不要指望两页讲同一件事：

| 话题 | 讲原理 | 查具体值 |
|---|---|---|
| 接口 | [API 与 SSE 契约](../design/api.md)：为什么是这个形状、SSE 怎么分帧、审批怎么续跑 | [HTTP 端点目录](api.md) |
| 配置 | [配置手册](../guide/configuration.md)：配置组的作用、边界、加载顺序与守卫 | [配置项参考](config.md) |
| 报错 | [故障排查](../ops/troubleshooting.md)：按症状组织的排查步骤 | [错误码与失败模式](errors.md) |

## 一份事实来源的提醒

这三页的内容来自代码，不是反过来。冲突时以代码为准，并且应该改这三页：

- 端点与请求响应模型 → `app/api/`、`app/schemas/`
- 配置项与默认值 → `app/config/settings.py`
- 错误码与错误文案 → `app/api/`、`app/services/`、`app/runtime/` 里的 `HTTPException` 与错误常量

`sql/init.sql` 是数据库结构的唯一事实来源，表名与字段以它为准，[数据模型](../design/data-model.md) 与这三页都跟着它走。
